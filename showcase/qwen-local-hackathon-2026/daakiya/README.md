# Daakiya (ڈاکیا): WhatsApp COD orders to courier bookings, on a CPU

Fine-tuned Qwen3-1.7B (QLoRA) that turns messy Pakistani order messages (English, Roman Urdu or mixed) into courier-ready booking JSON. Quantized to GGUF Q4_K_M (about 1.1 GB) and run on CPU only.

[Live CPU-only demo (free Colab, 2 vCPU, no GPU)](https://colab.research.google.com/github/mufeezhanif/daakiya/blob/main/demo/daakiya_cpu_demo.ipynb) · [GGUF](https://huggingface.co/someone786/daakiya-qwen3-1.7b-GGUF) · [LoRA adapter and full evidence](https://huggingface.co/someone786/daakiya-qwen3-1.7b-lora) · [Code, data and notebook](https://github.com/mufeezhanif/daakiya)

## What it does

The user is a small online seller who takes cash-on-delivery orders in WhatsApp or Instagram chat. They paste the customer's message, and Daakiya returns:

- `customer_name`: the parcel receiver, who may not be the sender.
- `phone`: normalized to `03XXXXXXXXX`. Invalid numbers and landlines are rejected.
- `city`: from aliases (lhr, khi, isb, pindi). Inferred from unique areas such as G-9/2. Set to `null` when the area exists in several cities, like DHA Phase 2.
- `area`, `address` ("House 23, Street 5, Block C") and `landmark` ("near Jamia Masjid").
- `items` with quantities, including Roman Urdu numbers ("do", "teen").
- `cod_amount`: understands 4.5k, 4,500/-, *dhai hazar*, *saadhe teen hazar*. Delivery charges are added, advances are subtracted, and a fully prepaid order gives 0.
- `payment`: `cod` or `prepaid`.
- `missing`: the required fields the seller still has to ask for.

The demo app turns `missing` into a Roman Urdu reply to the customer. It exports bookings as CSV for courier bulk upload.

## Why we built it

Sellers retype every chat order into a courier portal by hand. Customer messages mix languages, number formats and local shorthand. A wrong digit or an unconfirmed city means a failed COD delivery and a paid return.

A general model wasn't enough. With the identical system prompt, the base Qwen3-1.7B produced **0 booking-ready orders out of 208** test orders. It copied the example city from the prompt, took "AoA" (a greeting) as the name, and left phones unnormalized.

Fine-tuning a 1.7B model makes a cheap, private tool that runs on a shop's existing laptop. Customer phone numbers and addresses never go to a cloud API.

## Dataset

- **Source and license:** synthetic, generated by [`data/generate.py`](https://github.com/mufeezhanif/daakiya/blob/main/data/generate.py) under MIT. No real customer data was used. All names, phones and addresses are random.
- **Labels:** each label is computed from the same random specification that produced the message, so labels are exact by construction.
- **Coverage:**
  - nine training cities with aliases
  - real area, sector and block naming
  - nine areas that exist in several cities
  - ten phone formats
  - Roman Urdu money words
  - four message styles, including forwarded WhatsApp logs
  - corrections, recipients who aren't the sender, prepaid, advance and delivery-charge cases
  - missing and invalid fields
- **Splits:** 720 train, 60 validation, 100 in-distribution test.
- **Out-of-distribution test:** 80 orders from 7 cities never seen in training, with unseen phrasings and an unseen run-on style.
- **Hand-written test:** 28 messages written and labelled one by one. They include cases the generator never makes: a rural Chak address, a landline, an Urdu-script greeting, an all-caps message and a mother receiving her son's order.
- **Integrity:** no prompt appears in more than one split, and the notebook asserts this.

## Training

| Setting | Value |
| --- | --- |
| Base | `Qwen/Qwen3-1.7B` (Apache-2.0), revision `a972f4304f86` |
| Tool / platform | Unsloth on free Google Colab, Tesla T4 |
| Method | QLoRA on a 4-bit base: r 16, alpha 32, all attention and MLP projections, dropout 0 |
| Hyperparameters | 3 epochs, lr 2e-4 linear, warmup 5%, AdamW 8-bit, batch 4 × accumulation 2, seed 42, max length 1024 |
| Loss | Assistant answer only (`train_on_responses_only`), thinking disabled in the chat template |
| Versions | unsloth 2026.11.12, transformers 4.57.6, trl 0.22.2, torch 2.14.1 |
| Measured training time | 920 s, about 15.3 min (peak GPU memory 4.81 GB) |

## Run it locally

```bash
# Ollama, any laptop with about 2 GB of free RAM
ollama run hf.co/someone786/daakiya-qwen3-1.7b-GGUF:Q4_K_M

# or llama.cpp, CPU only
llama-server -hf someone786/daakiya-qwen3-1.7b-GGUF:Q4_K_M -c 2048 -ngl 0
```

For exact evaluation behaviour, use `models/Modelfile` from the GitHub repo. It pins the non-thinking Qwen3 template and the system prompt. The web app (`app/server.py`) talks to either runtime.

- Runtime: llama.cpp server (also Ollama)
- Quantization: Q4_K_M (recommended) and Q8_0
- Context: 2048
- Decoding: greedy

## Before and after

All comparisons use identical prompts, the system prompt above and greedy decoding. GPU numbers compare the 4-bit base with the adapter disabled against the same base with the adapter enabled, before export.

| Test set | Booking-ready (all courier fields exact) | Mean field accuracy | Valid JSON |
| --- | --- | --- | --- |
| In-distribution (100 orders) | 0.0% → **85.0%** | 47.8% → **97.7%** | 100.0% → 100.0% |
| Unseen cities and phrasing (80) | 0.0% → **35.0%** | 42.0% → **84.5%** | 100.0% → 100.0% |
| Hand-written messages (28) | 0.0% → **57.1%** | 62.9% → **91.8%** | 100.0% → 100.0% |

Per-field accuracy for every split is in the [GitHub README](https://github.com/mufeezhanif/daakiya#results). Every base and fine-tuned answer is in [`evidence/`](https://huggingface.co/someone786/daakiya-qwen3-1.7b-lora/tree/main/evidence).

CPU-only benchmark of the exported GGUF files: llama.cpp server with `-ngl 0` on a free Google Colab CPU runtime (Intel Xeon @ 2.20GHz, 2 vCPU, 13.6 GB RAM), llama.cpp b12818, 28 hand-written orders.

| GGUF | File | RAM used | Seconds per order (median) | Generation speed | Booking-ready | Mean field accuracy |
| --- | --- | --- | --- | --- | --- | --- |
| Fine-tuned Q4_K_M | 1.11 GB | 2.14 GB | 26.4 s | 4.9 tok/s | 46.4% | 87.5% |

Measured with [demo/daakiya_cpu_demo.ipynb](https://github.com/mufeezhanif/daakiya/blob/main/demo/daakiya_cpu_demo.ipynb), which anyone can rerun on a free Colab CPU runtime.

Held-out example (hand-written test):

> bhai DHA phase 2 mein bhejna hai, house 40 lane 3, number 03458876543, naam Hamza. 2 perfume 100ml, total 5000

- **Base:** `{"customer_name": "Hamza", "phone": "03458876543", "city": "Islamabad", "area": "DHA Phase 2", "address": "House 40, Lane 3", "landmark": null, "items": [{"name": "perfume", "qty": 2}], "cod_amount": 5000, "payment": "cod", "missing": ["city", "address"]}`. It guessed Islamabad for an area that exists in three cities, asked for an address it already had, and dropped "100ml".
- **Fine-tuned:** `{"customer_name": "Hamza", "phone": "03458876543", "city": null, "area": "DHA Phase 2", "address": "House 40, Lane 3", "landmark": null, "items": [{"name": "perfume 100ml", "qty": 2}], "cod_amount": 5000, "payment": "cod", "missing": ["city"]}`. It left the city empty and asked only for the city.

**How we judged:** [`eval/score.py`](https://github.com/mufeezhanif/daakiya/blob/main/eval/score.py).
- An answer counts only if it is valid JSON.
- Phone, payment and COD amount must match exactly.
- Name and city ignore case.
- Area, address and landmark ignore punctuation and spacing.
- Items compare as a multiset, and missing as a set.
- "Booking-ready" requires every courier-critical field to be exactly right.

**A failure:** in "pindi, chaklala scheme 3, … 1 school bag, dhai hazar", every field is right except `cod_amount`. The model returned 2000; *dhai hazar* is 2500. Spoken money is still the weakest skill: *saadhe chaar hazar* became 4400 and *chay hazar* became 3000. Other misses:
- an advance payment read as fully prepaid
- a `0092-` phone that was not normalized
- "Main Kashif bol raha hoon, parcel meri ammi … ke naam pe", where the sender was picked as the receiver
- a Chak/Tehsil rural address mapped to the district

Cities never seen in training are the biggest gap: city accuracy is 62.5% there, against 92% in-distribution.

## What we learned

- **Base failures:** the base model fails on conventions, not language. It reads Roman Urdu fine. But it invents placeholder phones, copies the example from the prompt, and never says "I don't know which city". A small adapter fixed those habits.
- **Hand-written set:** it was the most informative test. Generated test sets are too clean, and the hand-written mistakes pointed at real gaps.
- **Quantization:** Q4_K_M on CPU kept most of the gain. Mean field accuracy was 87.5%, against 91.8% for the adapter on the 4-bit training base. Booking-ready fell from 57.1% to 46.4%, which is three of 28 orders. Every courier field must be exact, so small token-level drift shows up there first.
- **Uncertain:** how well it does on real seller chats. We have not tested real customer data, by design.
