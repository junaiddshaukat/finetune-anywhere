# Munshi

Offline bookkeeping for small Pakistani shops. A fine-tuned Qwen3 1.7B turns a shopkeeper's Roman-Urdu note into one ledger entry, and plain code keeps the balances.

Code: https://github.com/wadeedkhan1/munshi · Model: https://huggingface.co/wadeedkhan1/munshi-qwen3-1.7b-gguf · Demo: https://www.linkedin.com/posts/wadeedkhan_qwenlocalhackathon-qwen-finetuning-ugcPost-7532132908493541376-olv7/

## What it does

The user is the owner of a small kiryana (grocery) shop who keeps track of credit (*udhaar*), payments, sales, stock purchases and shop expenses. They type a note the way they would write it in a register or a WhatsApp message, for example `Ahmed ko 5 kilo chawal udhaar diye 1500 ka`. The model returns one JSON entry with `type`, `party`, `item`, `qty`, `unit` and `amount`:

```
{"type": "udhaar", "party": "Ahmed", "item": "chawal", "qty": 5, "unit": "kg", "amount": 1500}
```

The app (`ledger.py`) shows the entry, saves it to SQLite only after the user types `y`, and answers `hisaab` (who owes how much) with SQL.

## Why we built it

Most small shops still keep udhaar in a paper register or in notes on their phone. Totals are added by hand, and mistakes cost money. Shopkeepers write in Roman Urdu with their own spellings (`chawl`, `darjan`, `dedh hazar`, `10k`), so a generic model given only instructions does poorly: the base Qwen3 1.7B got 6% of held-out synthetic entries fully right with the same system prompt. Fine-tuning teaches the output format and the local vocabulary, while a small model keeps it offline on a shop's own laptop. The model only extracts. It never does arithmetic, and nothing is saved without the user's confirmation.

## Dataset

- **Source:** synthetic, generated by `generate_dataset.py` (seed 42) from hand-written templates, names, items, units and amount phrasings. No personal or scraped data. Published with the code: https://github.com/wadeedkhan1/munshi/tree/master/data
- **Splits:** 1500 train / 150 validation / 150 evaluation, in chat format (system, user, assistant). The evaluation split uses held-out customer names, held-out items and held-out phrasings, and no evaluation message appears in train or validation (checked by `tests/test_leakage.py`).
- **Real check:** 50 hand-written messages in the way people actually type (`data/real_eval.txt`: udhaar 15, payment 11, sale 9, expense 8, purchase 7), never used for training.
- **Review:** every split was checked for duplicates, repeated prompts, cross-split leakage and length (longest example about 177 tokens).

## Training

- **Tool:** finetune-anywhere (commit f0cfd05), `paths/nvidia-gpu/train_unsloth.py`, Unsloth QLoRA
- **Platform:** local NVIDIA RTX 5060 (8 GB), Windows 11 with WSL2 Ubuntu 22.04, Python 3.11
- **Base:** `Qwen/Qwen3-1.7B` (finetune-anywhere `starter` alias), loaded as `unsloth/Qwen3-1.7B-unsloth-bnb-4bit` revision a972f4304f86a0a705d35b378d7a7675d58063a7
- **Hyperparameters:** LoRA rank 16, alpha 32, dropout 0, all attention and MLP projections; learning rate 2e-4, linear decay with warm-up; 3 epochs (1125 steps); batch size 1, gradient accumulation 4; max sequence length 1024; seed 42
- **Versions:** unsloth 2026.11.7, torch 2.8.0 (CUDA 12.8), transformers 5.17.0, trl 1.15.0, peft 0.22.0, datasets 4.8.5
- **Duration:** 1265 s of training (21 minutes), using about 3 GB of VRAM. Final train loss 0.068; validation loss 0.110 after epoch 1 and 0.097 after epoch 3.
- **Export:** merged and converted to GGUF Q4_K_M (1.1 GB) with Unsloth's llama.cpp converter

## Run it locally

Runtime: Ollama (tested with 0.40.18). Quantization: Q4_K_M. Context length: 2048. Memory: about 1.4 GB loaded in Ollama. Tested on an RTX 5060 (8 GB) at about 2.2 s per message; CPU-only speed was not measured.

```bash
git clone https://github.com/wadeedkhan1/munshi && cd munshi
pip install huggingface_hub
hf download wadeedkhan1/munshi-qwen3-1.7b-gguf finetuned-q4_k_m.gguf --local-dir .
ollama create munshi -f Modelfile
python ledger.py
```

Type a message, or `hisaab`, `list` or `exit`. The scripts need only the Python standard library.

System prompt (built into the `Modelfile` and sent by `ledger.py`):

```
You turn a shopkeeper's Roman Urdu message into one ledger entry. Reply with JSON only, with exactly these keys: "type" (one of "udhaar", "payment", "sale", "purchase", "expense"), "party" (person or supplier name, or null), "item" (standard item name, or null), "qty" (number or null), "unit" (kg, litre, packet, dozen, bori, piece, or null), "amount" (rupees as a number, or null).
```

## Before and after

All numbers come from `evaluate.py`: temperature 0, Ollama, the same system prompt for every model, on messages held out from training. Exact match means all six fields are right.

| Model | Synthetic eval (150) | Real hand-written (50) |
|---|---|---|
| Munshi (fine-tuned Qwen3 1.7B, 1.1 GB) | 94/150 (63%) | 34/50 (68%) |
| Base Qwen3 1.7B | 9/150 (6%) | 16/50 (32%) |
| Qwen2.5 7B (not fine-tuned) | 46/150 (31%) | 31/50 (62%) |
| Llama 3.2 3B (not fine-tuned) | 5/150 (3%) | 3/50 (6%) |

Same held-out prompts, real outputs:

| Prompt | Base Qwen3 1.7B | Munshi |
|---|---|---|
| `Mumtaz se 2000 mil gaye` | `{"type": "sale", "party": "Mumtaz", "item": "2000", "qty": 2000, "unit": "mil", "amount": 2000}` | `{"type": "payment", "party": "Mumtaz", "item": null, "qty": null, "unit": null, "amount": 2000}` |
| `dukan ki safai 300` | `{"type": "expense", "party": "dukan ki safai", "item": "safai", "qty": 300, "unit": "unit", "amount": 300}` | `{"type": "expense", "party": null, "item": "safai", "qty": null, "unit": null, "amount": 300}` |
| `Kamal ko 3 litre doodh udhaar` | `{"type": "udhaar", "party": "Kamal", "item": "doodh", "qty": 3, "unit": "litre", "amount": 0}` | `{"type": "udhaar", "party": "Kamal", "item": "doodh", "qty": 3, "unit": "litre", "amount": null}` |

**Failures and limitations:**
- The most common error is a customer payment labelled as udhaar: 12/150 synthetic and 4/50 real, for example `Junaid ne pichla hisaab clear kar diya 3200`. That would increase a balance instead of reducing it, which is why the app asks for confirmation before saving.
- Sales with the verb `bechi` or with no price (`5 kilo cheeni bechi`) can come out as `purchase`: the training data only uses `becha`, always with a price.
- On the real set the fine-tuned model is only slightly ahead of the 4x larger Qwen2.5 7B (34 vs 31 of 50). The 7B is better at the transaction type on the synthetic set (89% vs 81%) but often keeps the item as written instead of the standard name.

## What we learned

- The system prompt alone did not teach the format or the vocabulary. The same prompt gave 6% (base) and 63% (fine-tuned), and the biggest gains were in item names, units and leaving `amount` empty instead of guessing.
- A test set written by hand mattered. Base-model accuracy was 6% on synthetic messages and 32% on real ones, so synthetic numbers alone would have told a misleading story.
- Testing the model in a chat app showed that it depends on the system prompt. Without it, it produced unrelated JSON. Building the prompt into the `Modelfile` fixed that.
- Local training on Windows worked through WSL2, but needed more disk space and memory than expected. A full drive crashed WSL during the GGUF export, and short network drops broke the merge step until the base weights were downloaded in advance.
- Uncertain: how the model handles messages with several items, Urdu script, or vocabulary outside the 12 training items. The real set is small (50), so its percentages move a lot with a few messages.
